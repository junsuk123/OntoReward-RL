# Theory and implementation map

## 1. Frames and state
The simulator uses an inertial ENU-like frame with **z up** and a body FLU frame (**x forward, y left, z up**).
The rigid-body state is

`x = [p_I(3), v_I(3), q_BI(4), omega_B(3), omega_rotor(4)]`.

The first 13 states are the 6-DOF rigid body; the last four states model motor-speed dynamics.

## 2. 6-DOF equations

- `p_dot = v`
- `m v_dot = R_BI (F_rotor + F_aero) + m g_I`
- `q_dot = 0.5 Omega(omega_B) q`
- `J omega_dot = M_rotor + M_aero - omega x (J omega)`
- `omegaRotor_dot = (omegaCmd - omegaRotor)/tauMotor`

The code uses fixed-step RK4 at 50 Hz by default.

## 3. Distributed surface aerodynamics
Each fuselage/arm surface is discretized into panels. Every panel has its own center, normal, area and characteristic length.
At panel `i`, the local air-relative velocity is computed from the spatial wind field and rigid-body point velocity:

`v_rel,I = w_I(x_panel,t) - [v_I + R_BI(omega_B x r_i)]`

Then it is rotated to body coordinates. The normal pressure contribution is

`F_n = 0.5 rho Cd A v_n |v_n| n`.

Tangential skin friction uses a Reynolds-number-dependent `Cf`, with laminar/turbulent approximations. Panel moments are `r_i x F_i` and are summed. This is substantially richer than one global drag vector, but it is still a panel/lumped aerodynamic model, **not CFD**.

## 4. Wind field
`wind.sampleField` sums:
1. altitude-dependent mean shear,
2. deterministic 3-D Fourier turbulence modes,
3. localized spatiotemporal Gaussian gust packets with different vectors,
4. a finite-core vertical vortex.

Because every surface panel samples its own position, different parts of the drone experience different instantaneous wind vectors and therefore different forces/moments.

## 5. Paper-aligned semantic features
The user's landing paper defines Drone State, Wind State and Landing Pad Observation, and derives wind risk, alignment and visual stability before AI decision-making. This project preserves that framing. Wind risk uses normalized drag, wind acceleration and wind-direction change, followed by a configurable sigmoid encoding.

## 6. Ontology graph
Nodes encode PositionError, VerticalSpeed, TiltAngle, AngularRate, WindRisk, MarkerQuality, VisualStability, Alignment, AttitudeStability, TouchdownSafety and SafeLanding.
Relations are typed as `degrades`, `supports`, `contributes`, plus `self` loops.

The ontology fixes **what can relate to what**. R-GAT learns **context-dependent importance within those permitted relations**.

## 7. Relation-aware graph attention
For each relation `r`, the model has its own transform `W_r` and relation embedding `e_r`. Destination-normalized attention is computed only over incoming ontology edges. Two R-GAT layers produce the latent state of the `SafeLanding` goal node, and a bounded scalar potential `Phi(G)` is predicted.

Important: attention is an importance mechanism, not proof of physical causality.

## 8. Potential-based reward shaping
The proposed reward is

`r = r_sparse + lambda [ gamma Phi(G_{t+1}) - Phi(G_t) ]`.

At an absorbing terminal state `Phi=0`. The R-GAT is pretrained from future safe/unsafe landing outcomes generated by perturbed controller rollouts; it does not train on the hand-weighted baseline reward.

## 9. PPO
A custom continuous-action PPO implementation is included so only MATLAB + Deep Learning Toolbox are required. The actor outputs a tanh-squashed Gaussian over four high-level commands: collective, roll, pitch and yaw-rate. A low-level attitude controller and physical mixer turn those commands into four rotor speeds.

## 10. Independent evaluation
Training rewards are not used as paper metrics. Both agents are evaluated on common random seeds using the same physical success criteria: touchdown position, vertical speed, tilt and angular rate. The code also reports aerodynamic loads and an ideal induced-power energy proxy.
